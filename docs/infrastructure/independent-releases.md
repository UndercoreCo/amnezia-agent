# Независимый выпуск приложений Undercore

Применено 01.10.2026: platform `1e3b6dc`, API bundles `3134997`; [release report](../release/orchestrator-2026-10-01.md). Перечисленные ниже preflight/rollback правила остаются обязательными для каждого следующего выпуска. Native AWG acceptance и общий стенд текущего выпуска завершены.

Платформу, WireGuard API и Amnezia API можно готовить и выпускать отдельно. Этот порядок отделяет обновление кода от изменения VPN-адресов, клиентских ключей и инфраструктуры. Он описывает подготовленные исходники на 1 октября 2026 года; публикация требует отдельного согласования. Инструмент сборки не подключается к серверам и ничего не устанавливает.

## Что выпускается отдельно

| Компонент | Артефакт | Что остаётся на месте |
| --- | --- | --- |
| Платформа | Образы `wg-platform:<Git SHA>` и `wg-web:<тот же SHA>` | MariaDB, Redis, uploads, ключи и настройки |
| WireGuard Config API | Отдельный архив исходников, тестов, locked dependencies и спецификаций | SQLite, credentials, native wg-easy и VPN-туннели |
| Amnezia Config API | Свой архив исходников, тестов, locked dependencies и спецификаций | Keystore, node environment, агент и VPN-контейнер, если их обновление не требуется |
| iOS | Сборка Xcode | Самостоятельный клиент; выпуск backend не требует переустановки приложения |

Laravel API сайта и телефона остаются в платформе. Разделять их бизнес-модель и БД сейчас не нужно. Registry узлов — часть платформы, а не отдельный сервис с ещё одной базой. Адрес подключения самого VPN задаётся на соответствующем узле; его смена проходит [публикацию новой версии](../platform/vpn-configuration-releases.md).

## Сборка и проверка VPN API

Сборщик: [`infrastructure/releases/service_release.py`](../../infrastructure/releases/service_release.py). Запускать из корня WG. Выходной каталог должен уже существовать и находиться вне исходников. Пример ниже использует временный каталог только для локальной проверки, не как постоянное хранилище релизов.

```sh
mkdir -p /private/tmp/undercore-release
python3 infrastructure/releases/service_release.py build \
  --component wg-config-api \
  --output /private/tmp/undercore-release/wg-config-api.tar.gz
```

Для Amnezia заменить компонент на `amnezia-config-api` и выбрать другое имя архива. Обычная сборка требует чистого Git checkout; каждый включённый файл сверяется с blob указанного commit. Новый архив не перезаписывает существующий.

Для проверки незакоммиченных изменений допустим `--candidate`. Такой архив явно помечен как черновик и не проходит production-проверку `--require-committed`. Сборка черновика не заменяет выпуск конкретного проверенного commit.

Команда возвращает краткий JSON с Git SHA, контрольной суммой, числом файлов и признаком черновика. Внутри `release.json` перечислены точные имена, размеры и SHA256 файлов. В архив входит только положительно заданный список: все runtime-модули выбранного приложения, его тесты и README, проверяемые ими operator helpers (`retire_missing.py` у WG, `deploy/prepare.py` у AWG), AWG systemd units и boundary.Dockerfile (только файлы, без установки), `requirements.lock`, три спецификации, baseline, проверка контрактов с locked dependencies и эта инструкция. Другой сервис, `.env`, базы, ключи, `.venv`, caches и uploads не включаются. Наличие operator helper в архиве не разрешает запускать его на рабочих данных: тесты вызывают его только с синтетическими fixtures; обновление приложения не запускает retirement или initial prepare.

```sh
python3 infrastructure/releases/service_release.py verify \
  --component wg-config-api \
  --archive /private/tmp/undercore-release/wg-config-api.tar.gz \
  --sha256 <SHA256_ИЗ_ДОВЕРЕННОГО_ОТЧЁТА_СБОРКИ> \
  --require-committed
```

Проверка ограничивает размер сжатого и распакованного содержимого, сверяет полный состав, заголовки и хеш каждого файла; отвергает ссылки, специальные файлы, лишние записи и скрытые данные после конца архива. Она не распаковывает архив и не запускает приложения. SHA256 доказывает целостность относительно ожидаемой суммы, но не удостоверяет автора: архив и сумму нужно получить из доверенного CI/отчёта своего commit. Сам `source_state: committed` не является цифровой подписью.

После проверки распаковать **свой доверенный артефакт** в отдельный staging-каталог, создать там изолированное окружение с его `requirements.lock` и `contracts/requirements.lock`; повторить тесты выбранного сервиса и `contracts/check.py`. Тесты используют синтетические данные. Это не проверка настоящего Linux-туннеля, оплаты или миграции production-БД.

## Подготовка в CI

[`release-images.yml`](../../.github/workflows/release-images.yml) запускается вручную. Выбрать `component`: `platform`, `wg-config-api` или `amnezia-config-api`.

- `platform` собирает и проверяет application/web. MariaDB и Redis включаются только при отдельном `include_infrastructure`; для обычного выпуска сохранить их прежние image tags. Артефакт содержит контрольную сумму и список образов.
- VPN API проверяет исходники выбранного сервиса, совместимость спецификаций и тесты сборщика. Затем собирает committed-архив вне checkout, проверяет его и повторяет тесты из распакованного артефакта. Результат содержит архив, SHA256 и краткий отчёт сборки.

Workflow не выполняет SSH, deploy или изменение настроек. Артефакты Actions хранятся 7 дней: принятый выпуск и совместимую версию для отката нужно отдельно сохранить в закрытом release-хранилище. Существующий CI всех компонентов остаётся общим барьером перед выпуском накопленных изменений.

## Общий порядок установки

1. Зафиксировать текущие версии, runtime-настройки, состояние очередей и успешную свежую резервную копию. Для данных использовать [существующее резервирование](../../infrastructure/backups/README.md). Проверить место, совместимость схемы и ограничения отката ниже.
2. Подготовить отдельный каталог следующей версии, проверить доверенную сумму и состав, установить зависимости из lock в новое окружение. Не модифицировать работающий каталог по файлу за раз. Сохранить предыдущие код и окружение. Миграции и изменения environment перечислить заранее.
3. После согласования переключить только выбранный компонент. Не запускать initial-bootstrap скрипты, не менять credentials или endpoint вместе с кодом. Если требуется остановка writers/агента, заранее определить окно обслуживания.
4. Проверить readiness, авторизованный read-only health, наличие нового безопасного номера запроса и отсутствие новых ошибок/задолженности очереди. Реальные выдача, продление, отзыв и оплата допускаются только в согласованном тестовом сценарии. Зафиксировать версии и результат.
5. При ошибке выбрать совместимый возврат кода либо исправление вперёд. Не восстанавливать старую БД автоматически поверх новых оплат, issued peers или revocation history.

Документ задаёт порядок; автоматического установщика/переключателя на сервере пока нет. Пути, имена live units и права следует проверить перед конкретным согласованным выпуском.

## Платформа

Application и web должны использовать один Git SHA. Обновляются все PHP-роли: platform, worker, worker-amnezia при включённом профиле и scheduler; иначе очередь может исполнять старый код. Сохранить `WG_DATABASE_RELEASE` и `WG_REDIS_RELEASE` явно: их fallback на общий `WG_RELEASE` не должен неожиданно потребовать обновление БД/Redis.

Сначала подготовить образы и проверить public assets/readiness, затем остановить writers с учётом `stop_grace_period`, сделать согласованную копию и применить только заранее принятые миграции. После переключения проверить cache конфигурации и запустить все роли. Использовать точные image tags и `--no-build`; полный `compose up` или старый `scripts/deploy-production.sh` не заменяет этот порядок.

Для новых исходников нужна аддитивная миграция двух таблиц версий конфигураций. Первое включение сохраняет revision 1, прежние keys/default/API URL и VPN endpoint; оно не публикует новую версию и не отправляет кампанию автоматически. Проверка миграции и блокировок в MariaDB/Redis остаётся отдельным этапом.

Диагностика в production Compose настроена в два места: безопасный JSON в stderr и daily-файлы в постоянном `app-diagnostics` volume, общем для PHP-ролей. Файлы создаются с правами `0600`, запись использует lock, ротация — 14 файлов по дням. При первом запуске Docker копирует каталог образа с владельцем www-data; возможность записи UID 33 надо проверить на стенде. Volume сохраняется при пересоздании контейнеров, но не переживает удаление volume/хоста. `compose down -v` для выпуска недопустим. Docker stderr отдельно ограничен 3 × 10 MB на контейнер и исчезает при его удалении; это не долговечное хранилище.

14 файлов не означают предел в байтах или гарантированные 14 дней при отсутствии записей. Перед выпуском определить дисковый бюджет и проверить существующие disk alerts. Журналы не заменяют backup; обычные журналы/ошибки вне dedicated diagnostics не становятся автоматически очищенными от персональных данных. [Подробности диагностики](request-diagnostics.md).

## WireGuard API

Код находится в `/opt/wg-config-api/app`, зависимости — в отдельном окружении, state — в `/var/lib/wg-config-api/clients.sqlite3`, credentials — вне кода. Подготовить соседнюю версию и окружение, проверить реальные systemd working directory/ExecStart, затем переключить HTTP-фасад. Native wg-easy, cron истечения и tunnel не перезапускать ради обновления Python API.

Исторический `services/wg-config-api/manifest.json` и `deploy_connection.py` описывают прежнюю точечную операцию. Их хеши не соответствуют новому полному дереву; не использовать как установщик этого релиза. В новой сборке присутствуют `diagnostics.py`, `retirement.py` и все остальные runtime-модули.

После первого operator retirement откат к коду без tombstones/retirement guards запрещён. Проверить совместимость прежнего SQLite state; health сам по себе не доказывает сохранение идемпотентности и отзыва. Если предыдущая версия несовместима, выпускать исправление вперёд.

## Amnezia API и агент

Текущий deployment использует `/opt/amnezia-config-api/current` и отдельное окружение; HTTP работает от `awg-api`, привилегированный агент — отдельно. Проверить фактические пути units перед переключением.

Новый privilege split требует полного согласованного перехода по [AWG boundary](awg-privilege-boundary.md), трёх units и отдельного UID; частичная установка недопустима. Новые Linux tests используют синтетический native backend и не заменяют systemd/AWG приёмку.

Обновление только HTTP без перезапуска агента допустимо, когда `agent.py`, `backend.py`, `domain.py`, `export.py`, `local_rpc.py`, `runtime.py`, `runtime_client.py` и зависимости не изменены относительно live release и Unix RPC совместим. Зафиксировать это сравнением manifest/хешей до выпуска. Для HTTP можно использовать новое окружение, оставив работающий агент и его окружение на месте.

Если меняются агент, общие модули, RPC или его зависимости, нужен отдельный план обслуживания и проверка восстановления peers/истечения. В текущем unit `ExecStopPost` останавливает VPN-контейнер: рестарт агента может прервать VPN. Нельзя обещать отсутствие перерыва или рестартовать его вместе с HTTP вслепую. Сначала испытать сценарий на отдельном Linux-узле. `deploy/prepare.py` предназначен для первой установки и создания секретов; при обновлении его не запускать. Keystore, native image и node environment не заменяются source-архивом.

## Ограничения отката

| Состояние | Допустимый подход |
| --- | --- |
| Новый код ещё не обслуживал новые схемы/узлы, прежний код совместим | Возврат проверенных code/image + dependencies; сохранить данные и настройки |
| Есть доступы или принятые заказы на дополнительные узлы | Нельзя возвращать старую жёсткую карту primary; сохранить registry-aware код |
| Опубликованы managed configuration revisions | Нельзя отключить export guard; возврат VPN endpoint получает следующий revision, history/snapshots сохраняются |
| Есть retirement tombstones WG | Только код с retirement guards; старую SQLite поверх текущей не восстанавливать |
| Изменены AWG agent/RPC/native state | Отдельное обслуживание и проверенный совместимый набор; предпочтительно исправление вперёд |

Откат кода и disaster recovery — разные операции. Восстановление данных требует сравнения новых оплат/выдач/отзывов и сверки с VPN-узлами; backup restore не означает автоматический запуск всех прежних peers.
